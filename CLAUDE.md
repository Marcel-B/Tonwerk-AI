# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

Tonwerk (formerly YuE UI; only the visible name changed, the repo, projects, paths, data folder `YuE UI`, `yueui.db` and the LaunchAgent label keep the old one so deploys and data stay put) is a web interface for YuE Studio (a native macOS app around the YuE2 music model), meant to be used remotely through Tailscale. An ASP.NET Core Minimal API runs YuE Studio's own Python worker as a child process and serves a Vue frontend under `/ui`. README.md (German) is the user documentation. The structure follows `~/repos/YuE_To_Logic` (same SpaProxy/Vite setup, `ClientAppEndpoints`, test style).

## Commands

Requires the .NET 10 SDK and Node.js 22.12+.

```sh

deploy/setup-mac.sh              # an empty Mac: Homebrew, .NET 10, Node, uv, ffmpeg, YuE2 from a YuE Studio checkout (ENGINE_REF) with models, then install.sh; --transcription, --voices, --speech, --images, --midi, --montage, --ace, --whisper, --all
deploy/install.sh                # publish + LaunchAgent (de.bvelop.yueui); deploy/uninstall.sh removes it
deploy/install-speech.sh         # the speech lab's Python environment with mlx-audio (--test: one take per model)

CI runs both in the job `Frontend tests`. Pass `-p:SkipClientAppBuild=true` to skip every npm step.

## Architecture

### The worker (`Worker/`)

`yue2_worker.py` lives in YuE Studio's installation (`~/Library/Application Support/YuE Studio/src/tools/`), not here. Its protocol is documented at the top of that file: JSON lines in on stdin (`generate`, `render`, `cancel`, `stop`, `quit`, `ping`), JSON events out on stdout (`ready`, `started`, `stage`, `progress`, `song`, `failed`, `idle`, `log`, `error`). Songs are addressed by the absolute path of their `audio.flac`; this app maps that to `run/songN` ids (`SongLibrary.IdFor`). Check that file when YuE Studio updates (its version is in `installed.json`). `deploy/setup-mac.sh` installs the engine without the app, following the app's `Installer.swift`: a git checkout of tonywestonuk/YuE-Studio at `ENGINE_REF` as `src/`, the Neural Engine bridge built with clang, an editable install into `env/` (the package version never changes between releases), the models through its `tools/download_models.py`; raise `ENGINE_REF` only after checking `SEAMS` against the new worker. `deploy/update.sh` (a LaunchAgent `setup-mac.sh` turns on, label `de.bvelop.yueui-watch` like `yue watch`, which it replaces) deploys new commits on main when `GET /api/busy` (`BusyInfo`: what a restart would cut off, waiting jobs excluded since they survive it) says idle, and runs `setup-mac.sh --update`, which repeats the last run's options (`setup-options` in the data folder) and reinstalls a component only when its pin changed (`recipe` files next to the separator and Seed-VC environments, `speech/recipe` with `install-speech.sh`'s checksum), so engine and package versions move only through commits here; a newer YuE Studio tag is only logged.

- `yueui_worker.py` – the extension the launcher runs in front of the worker (`python yueui_worker.py <yue2_worker.py>`, copied to the output). It imports the worker as a module and patches a few seams (listed in its `SEAMS`, checked against the worker's source at start): extra `generate` fields `full_steps`, `max_tokens` up to 15000, `abc_sampling` and `semantic_sampling`. Songs with different sampling must not share a token batch, which it arranges through `Song.needs_plan` (see `PlanKey`). If a seam changed it runs the worker unpatched and says `"yueui_extensions": false` in the ready event (`WorkerInfo.Extensions`). LoRAs have seams of their own (`LORA_SEAMS`): without them only LoRAs are off (`"yueui_lora": false`), and the iPhone seams (`REMOTE_SEAMS`) may be missing altogether, since YuE Studio before 0.4, which the app may still have installed, has no iPhone. After a YuE Studio update, run it once by hand and check for `true`.
- LoRAs (`Worker/yueui_lora.py`, `yueui_lora_train.py`, `Loras/LoraLibrary.cs`, `LoraEndpoints`): YuE2 has no LoRA support upstream, so this app trains and applies its own, on the acoustic (NAR) path only: the AR path that writes score and song tokens stays untouched. `yueui_lora_train.py` (run by `deploy/train-lora.sh` with YuE Studio's Python, PyTorch on MPS) encodes songs with the VAE, computes the prompt's keys/values once through the AR half and then drops it, and trains LoRA pairs on the NAR projections with the flow-matching loss in the model's codec-dropout regime (`nar_velocity`'s `nar_cond_end`: the song tokens sit invisible between prompt and latents), since there is no released audio-to-song-token tokenizer; a check against `nar_velocity` gave identical velocities. Files keep Hugging Face names; ComfyUI's native layout (fused `qkv_proj`, `gate_up_proj`) is read too, a LoRA touching the AR path is refused. The worker extension takes `lora` (path) and `lora_strength`: `LoraSwitch` adds the deltas where the engines read NAR weights (`yue2.lean.nar_layer_state`, also bound into the Neural Engine runtime), changes the latent projections in place, drops the MLX weights and marks the ANE weight surfaces stale on a switch, and gates the scheduler so songs with different LoRAs never synthesize at once; LoRA songs skip the iPhone. The song's LoRA goes into `yueui.json` in its folder (renders read it, `SongRequest.Lora` too). The form picks from `GET /api/loras` (`<data folder>/loras/*.safetensors`, metadata read from the safetensors header). Untested on a Mac and with real weights.
- `YuePaths` – install root, output dir and the environment the worker needs (`YUE2_OUTPUT_DIR`, `HF_HOME`, `YUE2_ANE_CACHE`, …), copied from what the app passes its own worker.
- `PythonWorkerLauncher` / `IWorkerConnection` – process plumbing; tests replace `IWorkerLauncher` with `FakeLauncher` (`tests/.../TestApp.cs`).
- `WorkerHost` – singleton and hosted service. Starts the worker lazily on the first command, turns events into `SongState`s and a log, and hands both to `Status/StatusHub.cs` (`IWorkerStatus.Part`, events through `StatusHub.Publish`). `StatusHub` builds the snapshot and fans changes out to subscribers (bounded channels; a slow subscriber is dropped and its EventSource reconnects with a fresh snapshot); everything else in the works (drafts, queue, versions, stems, swaps, videos, covers, takes, the memory's holder) is kept there by whoever does the work through its `Update…` methods, so those services need not know the worker. The worker never calls the hub while holding its own lock, the hub asks the worker only under its own, so the two locks always come in the same order. It is registered through a factory (`Program.cs`) since the worker publishes through the hub and the hub reads the worker. Progress events are throttled per song. Each `SongState` keeps its stages with their start time (`Stages`, via `SongState.Entering`) and whether it is a render (`Render`, remembered from the render command since `started` does not say), which `SongTimeline.vue` shows with how long each stage took. If the process exits, running songs are marked failed and the next command starts a new worker.
- Transcription (SheetSage2) also goes through the worker: `{"cmd": "transcribe", "id", "audio", "task", "offline"}`, answered by `transcribe` events keyed by our id. The worker runs SheetSage2's own Python (`YUE2_SHEETSAGE_PYTHON`, see `YuePaths.SheetSagePython`), which YuE Studio installs, or `deploy/setup-mac.sh --transcription` the same way. `TranscriptionEndpoints` stores the upload in a temp folder that `WorkerHost` deletes when the transcription ends (the `JobQueue` when it leaves the queue unstarted); results are read from `<OutputDir>/transcriptions` by `TranscriptionLibrary`.
- YuE Studio runs its own worker (and model) when open; `IStudioDetector` reports that so the UI can warn. Two generating workers can exhaust memory.

### Lyrics (`Lyrics/`)

YuE2 only sings lyrics, it cannot write them. `LyricsWriter` drafts English or German lyrics (`LyricsLanguage`) in YuE2's format from keywords through an OpenAI-compatible server, by default LM Studio (`LyricsOptions`, section `Lyrics`); its system prompt holds the format rules. The default is `google/gemma-4-26b-a4b-qat` (~15 GB). The Mac has 24 GB and that model plus the usual open apps has frozen it in swap (the small `google/gemma-4-e4b` is the fallback), so a lyrics model and YuE2 are never loaded together: no draft while songs are busy, an idle YuE worker is shut down first, the model is loaded through `POST /api/v1/models/load` with `ContextLength` (LM Studio's just-in-time loading may pick the model's maximum context) and unloaded via `/api/v1/models/unload` right after, unless it was already loaded in LM Studio (then it is used and left alone); if LM Studio's guardrail refuses the load ("insufficient system resources"), other loaded models are unloaded, then the context is halved down to `MinContextLength` (the guardrail itself stays on, it is what prevents the freeze); while `LyricsWriter.IsWriting`, songs and renders wait in the `JobQueue`. If the server does not answer, `LmsCli` (`ILmStudioStarter`) runs `lms daemon up` and `lms server start`. The form picks the model from `GET /api/lyrics/models` (LM Studio's native `/api/v1/models` without embedding models, else the OpenAI-style `/v1/models`); a draft names it in `model`, otherwise `LyricsOptions.Model` applies, and the form stores an empty choice for the default so a changed default reaches it. A draft can take a photo (`image`, a JPEG/PNG/WebP data URL the browser scaled down in `photo.ts`) instead of or beside the keywords; it goes to the model as an OpenAI `image_url` part, and the picker marks models whose LM Studio `capabilities.vision` is set (`LyricsModel.Vision`). A draft takes long enough for a phone to lock or a proxy to drop the request, so `POST /api/lyrics` answers 202 and the draft runs in the background; `StatusHub.UpdateLyrics` keeps its `LyricsState` for the snapshot and publishes `lyrics` events, and the form remembers the id it asked for (`lyricsDraftId`) to take the result even after a reload. A request with `lyrics` and `instruction` revises that text instead of drafting (`LyricsRevision`, `LyricsWriter.RevisionPrompt`: change only what was asked, keep the rest word for word); the form offers it under the lyrics field and keeps the previous text in memory for an undo. `POST /api/quick` (`QuickSongs`, for an iPhone shortcut) queues a draft from `keywords` (German by default, the newest run's style unless `style` is sent) and keeps the song to make in `quick_songs` (schema version 23) by the draft's id; a hosted service listening like `AutoVersions` queues the song through `JobQueue.GenerateAsync` once the draft is done, and `PushNotifier` leaves out a quick draft's success, since the song's notification follows. Claude is offered too (`LyricsOptions.ClaudeModels`: Opus 5.5, Fable 5.1, Sonnet 5.5, Haiku 5.5, named by `ClaudeModelChoice.NameOf`, listed with `LyricsModel.Cloud` while the sketches' Anthropic key resolves, even when LM Studio is down): `ClaudeLyricsModel` (`ICloudLyricsModel`, the official SDK through the sketches' named `HttpClient` `anthropic`, adaptive thinking, `ClaudeEffort`) gets the same system and user prompts; such a draft claims no `ModelMemory`, stops no worker and skips the `JobQueue` (`JobQueue.LyricsAsync` starts it at once), so it runs beside songs. Tests fake LM Studio through the named `HttpClient` (`FakeLmStudio` in `TestApp.cs`) and Claude with `FakeCloudLyrics` (off unless a test sets `Configured`).

### Logic export (`Logic/`, `LogicEndpoints`)

`GET /api/songs/{run}/{song}/logic` converts the song's `score.abc` (`IScoreConverter`) and writes it with its `audio.flac` into a `.logicx` package (`ILogicProjectWriter`, `ZipLogicPackageSink` into a self-deleting temp file, since `ZipArchive` writes synchronously), in this process; warnings go in the `X-YueToLogic-Diagnostics` header (compact JSON of `Diagnostic`; the Logic page shortens them in German or English through `logic/logicNotes.ts`, voices without a template track as one note, which reads the English messages, so keep its patterns in step with `LogicProjectWriter`'s texts), a song that cannot become a project answers 422 with its errors. `LogicOptions` (section `Logic`) only has `SplitSections`. The way back is `POST /api/midi/abc`: a MIDI file (typically a song edited in Logic) goes through `IMidiToAbcConverter` and comes back as `MidiScore` (`abc` plus its warnings), which the library puts into the form with the song's style, lyrics and seed, or the advanced parameters as a bare score. The browser fetches the ZIP instead of following a link, so a refusal becomes a message and the warnings are readable. The tests run the real library.

The Logic page (yue-to-logic-pro's former web app) works from a library song (`song` = `run/songN`, the server reads its files) or an uploaded `score.abc` (+ optional FLAC): `POST /api/logic/convert` answers the `ConversionResult` (score with notes, MIDI as base64) for its preview, `POST /api/logic/export` the ZIP with its options, `splitSections` and `instruments` (track → name, port, channel; the export puts the track on that channel and, for outputs the template knows, on an External Instrument). These answer in `YueToLogicJsonContext`'s JSON (enums by name, `Warning`, `DrumMachine`), not this API's camelCase enums, because the page's frontend was written against it; `Instrument.Kind` carries its converter on the property since the global converter would win over one on the type. The instrument library (`SqliteInstrumentStore`, tables `instruments`, `track_assignments`; `InstrumentEndpoints`, same routes as yue-to-logic-pro) and the page's presets (`SqliteLogicPresetStore`, `logic_presets`, form kept as opaque JSON, names matched through an upper-cased `name_key`) are schema version 7. `POST /api/logic/import` takes over what yue-to-logic-pro's server kept (its `GET /api/instruments`, `/instruments/assignments` and `/presets` answers in one object), matched by name so it can run twice.

Backing vocals (`ArrangementOptions.Harmony`, `HarmonyGenerator`, track kind `Harmony`, names `Harmony …` which `MidiToAbcConverter` ignores) are an arrangement step after the doubling: parallel parts by scale steps that snap to a chord tone where the melody sits on one, a drone (the tonic per phrase, a phrase ending at a rest over a beat, in the melody's rhythm or held as `DroneHeld`), and choir parts (alto, tenor, bass) voiced per melody note by a cost over movement, register, missing chord tones, doubled third and parallel perfects. The key is the score's where the melody fits it, else `KeyFinder` (Krumhansl-Schmuckler), or the chosen one; a score without chord symbols gets them from `ChordGuesser` (triads of the key per half bar). The Logic page's upload also takes a MIDI file (`OpenScoreAsync` detects `MThd` and converts it to ABC first, its diagnostics joined to the conversion's), so a melody goes in and a MIDI with the parts comes out. The tool page `HarmonyPage.vue` (view `harmony`, under tools, loaded like the Logic page) does just that with the same `/api/logic/convert` and `ScorePreview`, only the harmony options switched on; its settings are per browser (`yue-ui.harmony`).

The preview's browser sound is a small synthesizer (`logic/synth.ts`: two oscillators, the `square` one a pulse with width and PWM built from a sawtooth minus its delayed copy since Web Audio has no pulse wave, the delay moved by the LFO (switchable) and by the amp and filter envelopes, each drawn a second time on a `ConstantSourceNode`, noise, filter, amp and filter ADSR, LFO), played for every pitched note routed to the browser; drums keep their noise kit. A patch's `engine` picks it or the FM synthesizer (`logic/fm.ts`: four sine operators after the TX81Z, its eight algorithms as data in `ALGORITHMS`, an envelope per operator, feedback on operator 4 as a `PeriodicWave` computed from the feedback loop since Web Audio cannot close a loop inside one render quantum); patches without `engine` are analog. `envelope.ts` holds what both share, `AnalogPanel.vue` and `FmPanel.vue` their controls, `SynthEditor.vue` both with the switch between them. They look like the Logic plugin (Marcel-B/Synth): framed modules (`SynthModule.vue`) laid into one grid with the effects, rotary knobs (`SynthKnob.vue`, dragged up or right, arrow keys, `touch-action: none` so only the knob takes the finger), waveform icons in the wave switches (`WaveIcon.vue`), each envelope's shape above its knobs (`EnvelopeCurve.vue`), and the FM algorithm drawn as operator boxes that also pick the operator being edited (`AlgorithmDiagram.vue`). A patch's `fx` (delay and reverb, `logic/effects.ts`, `EffectsPanel.vue`) cannot be built per note like the voice, since a tail rings past its note: every channel strip starts with an `EffectsChain` (sends; reverb a `ConvolverNode` on a generated noise impulse, delay with a lowpass in its feedback loop) that takes the playing patch's settings with each note, and so does the keyboard's output. `SynthScope.vue` draws an oscilloscope (triggered on a rising zero crossing) from `keyboardAnalyser()` on the instruments page. A patch is opaque JSON to the server (`normalizePatch` fills and clamps it in the browser). Each track's sound (`track_synths`, by track name) and named sounds (`synth_presets`) live in `SqliteSynthStore` (schema version 8, `SynthEndpoints`, `/api/logic/synths/...`). The Logic page's routing table has one choice per track (`choiceOf`/`choose` in `ScorePreview.vue`): the default sound, a named sound, or, where the browser has Web MIDI (Chromium, Firefox), a MIDI instrument (its assignment; elsewhere only one already assigned is listed); ports and channels are no longer picked by hand, and sounds are edited only on the instruments page. A track given a named sound stores its name and a copy: it follows the named sound while that exists (`patches`), the copy only covers a deleted one or a track sound made by an older version. `logic/synths.ts` holds both, and the output pool looks the patch up per note, so an edit is heard at once. It never reaches the MIDI file or the Logic project. Every track has a channel strip in the browser output (fader, `StereoPanner`, `AnalyserNode` for the meter) before the master; `MixerPanel.vue` sets volume and pan through `OutputPool.mixChanged` without touching the schedule, and reads the meters from `OutputPool.levels`. Its settings are one JSON row (`logic_mixer`, schema version 9, `/api/logic/synths/mixer`). Mute is the routing's `muted`, solo is kept in the page only; both take notes out of the schedule, so they apply to MIDI ports too.

The instruments page (`InstrumentsPage.vue`, view `instruments`, loaded like the Logic page) edits the MIDI instrument library (`InstrumentLibrary.vue`; the list is `logic/instrumentLibrary.ts`, shared with the Logic page, which only assigns tracks and links here) (each with a note behind the speech bubble, `SongNote.vue` with a `save` of its own: `PUT /api/instruments/{id}/note`, column `note`, schema version 19, never written by the form's save or the import) and the named sounds (`SoundLibrary.vue`), and plays either on `TestKeyboard.vue`. A key is held as long as it is down, which the synthesizers' scheduled envelopes do not know: `logic/keyboardVoice.ts` schedules the note long and cuts it with a gate that fades over the sound's release; MIDI instruments get note on and off on their port and channel. The page has one `MIDIAccess` (`midiAccess()` in `midiPlayer.ts`; Firefox closes a device when any of its port objects is collected, so never call `navigator.requestMIDIAccess` elsewhere); `rescanMidi` (the refresh buttons by the port picker and in the Logic page's routing) asks for a new one and keeps the old alive, since Firefox looks for devices only on a request, and `onMidiPortsChanged` reports that and every `statechange`. Ports Firefox could not name (its midir backend says `unknown input port`, seen on the Mac for devices switched on while it ran, even after a fresh request) are left out by `unreadablePort` and the page tells the user to restart Firefox, which is all that read them. Firefox also keeps a port by its name once seen and never takes a fresh one for it, so after devices changed while it ran an output can reach the wrong device (Mother32's output also played the drum machine on another, Logic sent it right); `listMidiPorts` compares the names with the page's first listing and says `restartFirefox`, and the same hint appears.

The preview also shows and plays the song's recording (`logic/recording.ts`): the library song's `audio.flac` (fetched from `/api/songs/{run}/{song}/audio`) or the uploaded FLAC is decoded once in the browser into 5 ms peaks, drawn as a lane of its own above the tracks (`pianoRoll.ts`, `WAVE_HEIGHT`) and played on its own `AudioContext` from the playhead, starting at `ScoreDocument.CountInTicks`. Switched off (per browser, `loadRecordingSettings`) nothing is fetched. `POST /api/logic/musicxml` answers the converted score as MusicXML (`IMusicXmlWriter` in the Core). The export's `stems` (a finished `StemSetState` of the library song) puts its `vocals` and `vocals_dry` on the template's two vocal audio tracks, decoded to 48 kHz 24-bit WAV by `IAudioMixer.DecodeWaveAsync` into a temp folder; the page preselects the song's newest such set and its "create stems" button opens `#/voices/<run>/songN` (`openStems`). Other stems have no template track.

The analyzers (`spectrum.ts`, `SpectrumBars.vue`): every place that plays in the browser registers a `SpectrumSource` (its `AnalyserNode`s, one per audio context since nodes cannot cross contexts, and its `playing` ref). The player routes its element through a `MediaElementSource` only when its analyzer is on, and only from a click (`player.ts` `listen`): iOS starts a context made outside one suspended, and a routed element then plays silence; it also sets `navigator.audioSession.type = 'playback'` so Web Audio keeps playing with the screen locked. A start from the element's controls or the lock screen comes as a `play` event outside the tap, where iOS refuses `resume()`, so a context suspended while the screen was locked would leave the song playing silently: the player bar has its own play button and every tap on the page wakes the context (`wake`). A context iOS suspended or interrupted can say `running` again and still stay silent, for the paused song and every new one, so `player.ts` makes the audio element itself (in `PlayerBar.vue`'s `audioHost`) and gives a graph that may be dead up together with its element: marked `stale` on a state change, on the page hiding while paused, or after a long pause, a start from our buttons (`freshStart`) routes a new element through a new context, and a start without our gesture (lock screen, the element's controls, a song ending there) goes on unrouted on a new element (`playUnrouted`), the analyzer resting until the next tap. Play and pause from the AirPods, the lock screen or Control Center have Media Session handlers of their own (`resumeRemotely`): WebKit runs them as a gesture, so a stale graph is swapped for an unrouted element there, before the start; left to iOS, the `play` event came after it and the swap outside a gesture lost the playing element for good. Only on iPhone and iPad (`touchWebKit`): Safari on the Mac played nothing through a context made after an earlier one was closed, so there the element keeps its one context. The full-screen player (`NowPlaying.vue`, mounted by `PlayerBar.vue` while `player.ts` `expanded`, so the audio element does not move for it) shows the cover large on a blurred copy (the drawn one from `export.ts` `drawCover` without a cover of its own), progress from `elapsed`/`duration` with `seek`, the run's lyrics, a large analyzer and glows in `coverColour`; its switches are `nowPlaying*` in the visual settings, and with analyzer or effects on it routes the element even when the small analyzer is off (`wantsAnalyser`). Opening pushes a history entry, so the back gesture closes it; a hash change closes it too. The small analyzer in `PlayerBar.vue` is also the button (`VisualsButton.vue`) for the switches; the Logic preview has a large one fed by `OutputPool.analysers()` and `RecordingPlayer.analyser`. `AudioBackground.vue` (setting `background`, off by default, never under `prefers-reduced-motion`) moves three glows behind the cards through transform and opacity only; `#app` has `isolation: isolate` so its `z-index: -1` stays above the body's background. The switches are per browser (`yue-ui.visuals` in `localStorage`).

### Lyrics timing (`Timing/`, `TimingEndpoints`)

When each line of a song's lyrics is sung, for the full-screen player and video subtitles. `LyricsTimer` (hosted service, subscribes like `AutoVersions`; `Timing:Auto`) has every ready song with lyrics heard once, older ones when the player asks (`POST /api/songs/{run}/{song}/timing`), one at a time. `WhisperListener` (`IWordListener`; tests use `FakeListener`) runs `Timing/yueui_whisper.py` with its own Python (`Timing:Python`, made by `deploy/install-whisper.sh`, `setup-mac.sh --whisper`, mlx-whisper pinned) once per song: large-v3 turbo with word timestamps, the lyrics' start as `initial_prompt`, the language from style or umlauts (`LyricsTimer.Language`), `condition_on_previous_text` off since songs repeat lines. It hears the song's newest vocal stem (`vocals_dry`, then `vocals`) where there is one, else the mix. Whisper is small (~1.6 GB) and claims no `ModelMemory` slot; it only waits while another large model holds it. `LyricsAligner` lays the lyrics' sung lines (tags and empty lines left out, `SungLines`; the frontend's `timing.ts` `shownLines` counts the same way) onto the heard words by a longest common subsequence with near-equal words alike (`Alike`), so a misheard word or a repeated chorus does not shift the lines; unheard lines share the gap between their neighbours, a line ends at the next one's start at most. Results are JSON files in `lyrics-timing/<run>/songN.json` next to the database (`TimingFiles`, deleted with the song), `GET .../timing` answers them with the state (`TimingAnswer`), `GET .../timing.srt` as SubRip. `NowPlaying.vue` asks once and polls while listening, lights the line (`lineAt`, until 4 s past its end), scrolls to it unless the user scrolled in the last 4 s, and seeks on a tap. Music videos take them too: `video.ts` `drawLyricsStrips` draws the lines into strips of `VideoLayout.LyricsPerStrip` band-sized slots under an empty one (one canvas for a whole song exceeds iOS's canvas limit), the endpoint checks their sizes against the server's own timing and writes the times (`VideoLayout.Cues`, shown until `LyricsLinger` past the line) as `lyrics.json` beside them, and `FfmpegVideoRenderer` crops each strip by a sum of `gte(t,…)*lt(t,…)` terms over the band, under the cover. Untested on a Mac and with real Whisper weights.

### Song traits (`Analysis/`, `SqliteSongTraitStore`)

### YueToLogic.Core (`src/YueToLogic.Core`)

Moved here with its history from yue-to-logic-pro (its API, CLI and the StemMyWav/ChangeMyVoice clients were left behind; this app has its own). It stays host-independent: no console, file system or logging, input is a `string`/`Stream`, output `byte[]` or a caller-supplied `Stream`, problems are `Diagnostic` records with stable codes `YTL0xx` (`DiagnosticCodes`; add a code, never reuse one) instead of exceptions. It is `IsAotCompatible`, so JSON goes through the source-generated `YueToLogicJsonContext`. `AddYueToLogic()` registers everything as stateless singletons.

- Pipeline (`ScoreConverter`): `ConversionOptionsValidator` → `AbcScoreParser` (YuE2's ABC dialect, lenient; an accidental holds for its letter in every octave until the bar line) → `ScoreArranger` (octave shifts, doubling, generated chords/bass/drums/guide tones, groove, mono, count-in; order documented in the class) → `MidiRenderer` (DryWetMidi, type 1). Track names (`Vocal`, `Ins`, `Chords`, `Bass`, `Drums`, `Guide`, …) key channels, programs, instruments and Logic template tracks alike.
- The way back (`MidiToAbcConverter`): `MidiFileReader` → track roles by name → sixteenth grid → `ChordTrackReader`/`ChordRecognizer` → `AbcScoreWriter`, which lays the score out exactly as YuE2 does; the tests hold it to character-for-character round trips of `samples/score.abc` (the official YuE2 example, copied into both test projects as `Samples/score.abc`).
- MusicXML (`MusicXml/MusicXmlWriter`): partwise 4.0, one single-voice part per track except the drums, cut into slices at every bar line and note start or end so overlaps become chords with ties; chord symbols (`harmony`), sections and tempo above the first part. Checked by `MusicXmlWriterTests` (every measure adds up to its bar) and once by opening the sample in music21, not yet in MuseScore.
- Logic writer (`Logic/`): Logic's format is undocumented. `LogicProjectWriter` patches a template saved by Logic Pro 12.4 (`Logic/Template/*`, embedded; tracks for the eight backing vocals by their names, MIDI outputs merged from two saves, see `LogicProjectWriter.Instruments.cs`); its partial-class files record byte offsets and how they were derived in their `<remarks>`, keep that style. The template decides which tracks exist (`YTL053`); routing a track to hardware swaps in Apple's External Instrument, only for MIDI outputs the template's Mac knew (`YTL055`). `LogicProjectWriterTests` checks the template's own song reproduces Logic's note bytes exactly; a new template must be saved from Logic, plists converted with `plutil -convert xml1`, and that test updated. Every change was verified by opening the result in Logic; there is no other oracle. Audio must be 48 kHz FLAC (mix) / WAV (stems).

### Voices (`Voices/`, `VoiceEndpoints`)

A finished song can be sung again with a reference voice: the song is separated into dry vocals, their reverb and the instrumental, the dry vocals are sung by Seed-VC with the voice, and `FfmpegMixer` (`IAudioMixer`) mixes the result at the original vocals' mean volume back under the instrumental, optionally with the reverb stem, as a 48 kHz FLAC. Both models run in this process's children: `MlxStemSeparator` runs `mlx-audio-separator` (ffmpeg to 44.1 kHz in, every stem out as 48 kHz WAV named after `stem-models.json`, StemMyWav's catalog embedded as `StemCatalog`; `MapStems` pairs the files' bracket labels with the catalog's stems as StemMyWav did, the dereverb model's `(noreverb)`/`(reverb)` become `vocals_dry`/`vocals_reverb`), `SeedVcVoices` runs `Voices/yueui_seedvc.py` (ChangeMyVoice's `changemyvoice_infer.py`, copied unchanged) with Seed-VC's own Python once per conversion and reports progress from ChangeMyVoice's time estimate (`EstimatedSeconds`); both go through `ToolProcess`. `deploy/setup-mac.sh --voices` installs each in its own environment under `VoiceOptions.ResolvedEngineRoot` (`<LocalApplicationData>/YuE UI/engines`), or points `appsettings.Production.json` at StemMyWav's and ChangeMyVoice's existing installations. Where a tool is missing (`VoiceOptions.LocalStems`, `LocalVoices`), the façades `StemSeparator` and `VoiceEngine` fall back to the old HTTP services, `StemClient` (StemMyWav's Mac API, `POST api/separate`, a ZIP of WAVs) and `VoiceClient` (ChangeMyVoice's `/api/v1/jobs`, polled), so a Mac deployed before `--voices` ran keeps working; tests fake those through the named `HttpClient`s and the local tools with shell scripts (`LocalEngineTests`). Reference voices of their own are in `reference_voices` (schema version 13, `SqliteReferenceVoiceStore`, 44.1 kHz mono WAVs of 3 to 25 s in `voices/` next to the database); with a local Seed-VC, `VoiceEngine` takes ChangeMyVoice's collection over once with its ids (marker `voices/.imported`, retried on the next listing while the service fails), so versions that name a voice keep finding it. The page `VoicesPanel.vue` lists, plays, uploads and deletes them.

The result is a version (`VersionState`), a file of this app's own under `versions/` next to the database with a row in `song_versions` (`SqliteVersionStore`), never written into YuE Studio's song folder. The row keeps what the version was made with (voice, shift, strength, steps, reverb and the stem model, which is taken from `VoiceOptions.StemModel` when it is asked for and used for it even if the setting changes later); the library shows that under each version. `SongLibrary` lists a song's versions in `SongInfo.Versions` and deletes them with the song. `VoiceConverter` is a hosted service with a queue that makes one version at a time, and only while neither the YuE worker nor `LyricsWriter` is busy: it shuts down an idle worker first, and while `IsConverting` songs, renders and lyrics wait in the `JobQueue`, like they do for the lyrics writer (24 GB are not enough for YuE2, separation and Seed-VC together). Progress goes through `StatusHub.UpdateVersion` as `version` events and into the snapshot; `PushNotifier` announces finished ones. After a restart, queued versions are queued again and half-made ones marked failed. The player plays a version as a `Track` with its own `src` and `songId` pointing at the song, so rating, playlist and the song's address stay the song's. A voice can also be chosen in the form (`GenerateRequest.Voice`, looked up when the song is asked for and carried as `SongVoice` in the queued job's payload, `JobQueue.VoiceKey`, and via `WorkerHost.ExpectSongs(voice)` onto the started songs' `SongState.Voice`); `AutoVersions` (hosted service, subscribes like `PushNotifier`) queues a version for each such song once it is ready. Renders never carry a voice. Only whole octaves are offered in the UI: any other shift sings out of key over the song's own accompaniment.

The voices page also splits songs into stems (`StemEndpoints`, `StemsPanel.vue`), which needs only the separator (`VoiceOptions.StemsConfigured`, `VoiceInfo.StemsConfigured`). A `StemSetState` waits in `VoiceConverter`'s queue (entries `stems:<id>`, same memory rules as a version), `StemSeparator.ExtractAsync` keeps every stem whatever the model makes, `WavPeaks` reads each one's waveform on the server (one scale per set, so the phone need not download stems to draw them), and `IAudioMixer.EncodeFlacAsync` stores it as 24-bit FLAC (the WAV where ffmpeg fails) in `stems/<id>/` next to the database (`SqliteStemStore`, `song_stems`, schema version 10). The model list is the embedded catalog (StemMyWav's `GET api/models` with the service, or only `StemModel` when that does not answer). Progress goes out as `stems` events and in the snapshot's `Stems`; `#/voices/<run>/songN` preselects a song. A file of one's own can be split too (`POST /api/stems`, multipart `file`, `model`, `dereverb`): its set has an empty `SongId` (`StemSetState.Upload`, the file name as `Title`), the upload waits as `source.*` in the set's folder, is decoded to FLAC when its turn comes and deleted once the stems are stored; a server stop leaves the folder so a waiting upload resumes. Stems are addressed by set alone (`/api/stems/{id}/{name}`, `DELETE /api/stems/{id}`, `/api/stems/{id}/{name}/midi`, an upload's MIDI at the tempo given since it has no score); the song's routes stay for pages loaded before. Tests fake both services through the named `HttpClient`s (`FakeVoiceService`, `FakeStems` in `TestApp.cs`) and the mixer (`FakeMixer`); `AudioMixerTests` runs the real ffmpeg when it is installed.

The voices page also sings an uploaded recording with a reference voice (`SwapEndpoints`, `VoiceSwapPanel.vue`, `SwapState`): a bare vocal track (the default) is decoded to 48 kHz WAV (`IAudioMixer.DecodeAsync`) and goes straight to Seed-VC, then to FLAC; a whole song (`separate`, needs `ConversionConfigured`) is decoded to FLAC, separated and mixed back like a version. It waits in `VoiceConverter`'s queue (entries `swap:<id>`, same memory rules), progress goes out as `swap` events and the snapshot's `Swaps` (the queue page lists them), the conversion settings travel as `VoiceConversion` (which `IVoiceBackend.ConvertAsync` takes for versions and swaps alike). Upload (`source.*`) and result (`result.flac`) lie in `swaps/<id>/` next to the database (`SqliteSwapStore`, `voice_swaps`, schema version 15), the page plays both to compare.

### Speech lab (`Speech/`, `SpeechEndpoints`)

A page for trying local text-to-speech models (a podcast is the idea; YuE2 only sings). `SpeechLab` (hosted service, like `VoiceConverter`) speaks one take at a time: a text, a model from `SpeechOptions.ResolvedModels` (`SpeechModel.Defaults`: Chatterbox Multilingual v3, Qwen3-TTS, Higgs Audio v2/v3, MOSS-TTS Local, all mlx-audio repos, replaceable under `Speech:Models`; Higgs v3 twice, `higgs-v3-calm` sampled more carefully and with `ContextPieces` to compare by ear, same repo and cache) and optionally a recorded voice to clone (`SpeechVoice`, 24 kHz mono WAV plus its transcript, which several models need). `MlxAudioEngine` (`ISpeechEngine`; tests use `FakeSpeech`) runs `Speech/yueui_speech.py` with the lab's own Python (`Speech:Python`, made by `deploy/install-speech.sh`, not YuE Studio's; it also installs PyTorch, which only Higgs Audio v3 needs, since mlx-audio reads its bfloat16 codec through it, and the script names a missing package as the take's error) once per take, so the model leaves the memory with the process; the script answers `YUEUI {json}` lines (stage, done with timings and peak memory) between mlx-audio's own output, whose `Error …` line becomes the take's message. It goes through mlx-audio's `generate_audio`, which hands every model `temperature=0.7` and `max_tokens=1200` over its own defaults (MOSS-TTS, which samples at 1.7, then speaks one line and chirps), so the script's `LabModel` passes those two only when a model's `Options` name them. Models that speak only ~40 s per generation (Chatterbox, Higgs v2/v3) have `ChunkCharacters`: `LabModel` speaks the text in pieces cut at sentence ends (`pieces`; not after numbers or short words, German dates and abbreviations), gives a heading a full stop, and without a recorded voice lets later pieces clone the first; with `ContextPieces` (only for a model that takes several reference clips, Higgs v3) the pieces just spoken go along as further references, an undocumented experiment. `guard_codes` keeps Higgs v3's begin/end-of-audio codes (1024/1025, which the sampler may draw where a codebook still owes a code, mostly at a piece's end) away from its codec, whose lookup has no bounds check and turned them into a short noise at sentence ends; the script's `note` events go to the server log. Models download into `Speech:ModelCache` (`HF_HOME`) on their first take. Browser recordings (WebM or MP4) go through ffmpeg (`PrepareVoiceAsync`: silence cut at both ends, 30 s at most). Memory: a take claims `ModelMemory` (`LargeModel.Speech`, see Queue), shuts an idle worker down, and the others wait while it holds it. Takes and voices are in `speech_takes`/`speech_voices` (schema version 11, `SqliteSpeechStore`), files in `speech/` next to the database. Progress goes out as `speech` events (`StatusHub.UpdateSpeech`), and takes in the works (plus the last finished one) are in the snapshot's `Speech`, so the queue page lists them after a reload (`QueueList.vue` with its own wait reason, `speechWaitReason`; `QueueOverview.vue`, there and on the create page, adds a fourth tile, `speech`, only while the lab has takes in the works; `queueCount` counts them); `SpeechLab.vue` loads `GET /api/speech` when shown and when the stream reopens and lays the events over it. A take can also clean a speech recording instead of speaking (`SpeechTake.Source`, the upload's name; "Sprache säubern", `SpeechCleanPanel.vue` at the page's end): `POST /api/speech/cleanups` (multipart `file`, `model`, up to 1 GB) decodes the upload with ffmpeg to 48 kHz mono WAV (`ISpeechEngine.PrepareRecordingAsync`, at most 2 h) into `speech/sources/<id>.wav` (deleted with the take, not backed up), and the take waits in the lab's line and memory like any other; `CleanAsync` runs the same script with `clean: true`, which loads one of mlx-audio's enhancement models (`SpeechModel.CleanDefaults`, replaceable under `Speech:CleanModels`: MossFormer2 SE 48K in 30 s pieces faded over 1 s, its repository lacking the `config.json` and `model.safetensors` mlx-audio asks for, so `mossformer_folder` links `model_fp32.safetensors` into a folder of its own under `HF_HOME`, DeepFilterNet 3 streamed with its state; mlx-audio 0.5.9 at least, which `install-speech.sh` asks for) and reports `progress` events (`SpeechTake.Progress`, schema version 24) and the stage `cleaning`; its time limit is `Speech:Timeout` plus the recording's length. `GET /api/speech/takes/{id}/source` plays the original. In desktop Chromium the cleanup card and the stems' file upload also record another tab's sound (`tabAudio.ts`, `TabRecordButton.vue`: `getDisplayMedia` with tab audio, only the audio track through `MediaRecorder` as Opus WebM, handed over as a chosen file; hidden where `userAgentData` or `getDisplayMedia` is missing, since Safari and Firefox share no tab sound and phones no screen). Tested in a Linux container with randomly initialised weights on MLX's CPU build, not on the Mac or with the real weights.

### Audio to MIDI (`AudioMidi/`, `AudioMidiEndpoints`)

A track to MIDI with Spotify's Basic Pitch, beside SheetSage2's transcription (which writes a score on the beat; this keeps the notes where they were sung). `BasicPitchEngine` (`IAudioMidiEngine`; tests use `FakeAudioMidi`, `BasicPitchEngineTests` run the real one when its Python is at the default place or `YUEUI_BASICPITCH_PYTHON`) runs `AudioMidi/yueui_basicpitch.py` with its own Python (`AudioMidi:Python`, made by `deploy/install-midi.sh`; `setup-mac.sh --midi` reruns it when its checksum changes), one process per track, one track at a time. Basic Pitch 0.4.0 asks for TensorFlow on Linux and CoreML on the Mac; the script runs its bundled ONNX model instead, so the package is installed `--no-deps` with its requirements pinned beside it (setuptools below 81, since resampy still imports `pkg_resources`), the same on the Mac and in a cloud container. The model is a few MB on the CPU, a song takes seconds, so it waits for none of the big models and is answered within the request: `POST /api/audio-midi` (an upload, decoded by `IAudioMixer.DecodeAsync` first, tempo given or 120) and `POST /api/songs/{run}/{song}/stems/{id}/{name}/midi` (a stem, tempo from the song's `Q:` field, read by a regex since the score parser assumes 120 without one), both answering the `.mid` with the note count in `X-Audio-Midi-Notes`. `AudioMidiSettings`: `mono` (the script's `single_line`: a quieter overlapping note is dropped or keeps what sticks out, a louder one cuts the one before short, since Basic Pitch hears overtones as notes), `quantize` (sixteenths of the tempo), `bends` (only with `mono`). Vocal stems (and uploads) are limited to 65–1400 Hz and named `Vocal`, so the Logic page and the backing vocals read the file as the melody; other stems keep their name (`Bass`, `Drums`). `AudioMidiKind` says which: a `bass` stem is always mono and limited to 30–400 Hz, a `drums` stem skips Basic Pitch (no pitches to hear) for the script's `drum_hits`: onsets from the summed band flux, each sorted by how suddenly (dB) and how far (share of the 90th percentile) its bands rose, kick below 120 Hz, snare 1.5–5 kHz, closed hi-hat above 8 kHz unless it is the snare, on GM notes 36/38/42; tested only on synthesized grooves. The Logic page takes them as `bassStems`/`drumStems` (a stem set id) on convert, MusicXML and export: `StemParts` makes each stem's MIDI once per tempo (kept in memory, a cancelled request leaves it running) and hands it to YueToLogic.Core as `ConversionOptions.Recorded` (`RecordedParts`, `[JsonIgnore]`, never from a request's JSON), where `RecordedPartReader` maps the file's seconds onto the score's ticks and the arranger lays the bass and drums in place of the generated ones (drums through `DrumPatternGenerator.Tracks`, so split tracks and a drum machine's notes apply), before groove, mono and count-in; diagnostic `YTL034`. The page offers it per stem with two checkboxes (`yue-ui.logicStemParts`), from the set picked for the vocals where it has the stem, else the newest that does. Frontend: `AudioMidiPanel.vue` under the transcription, a button by every stem in `StemsPanel.vue`, settings shared per browser in `audioMidi.ts` (`yue-ui.audioMidi`), `MidiResult.vue` saves through a real link and hands the file to the Logic page or `HarmonyPage.vue` through `view.ts`'s `handedMidi`, which both take as their upload. Tested in a Linux container with a synthesized voice, not yet on the Mac or with a real vocal stem.

### Queue (`Queue/`, `QueueEndpoints`)

`JobQueue` (hosted service) takes every song, render and lyrics draft instead of refusing it with 409 while another model holds the memory: songs and renders go to the worker (which queues and batches them itself) as soon as neither `LyricsWriter.IsWriting` nor `VoiceConverter.IsConverting`; a draft also needs the worker idle. Jobs start in order, bundled by model in one respect: while YuE2 is busy, songs and renders pass a draft waiting at the front and go to the worker (it batches them), until that draft has waited `QueueOptions.BundleWindow` (section `Queue`, default 20 min); a version waiting that long in `VoiceConverter` (`WaitingSince`) holds back new songs the same way. A job that can start at once is started inside the request, so a missing YuE Studio still answers 503; otherwise the request answers 202 with the `QueuedJob` (a draft with its `LyricsState` in stage `queued`, whose id the form keeps as `lyricsDraftId`). Waiting jobs are in `queued_jobs` (`SqliteJobStore`, job and payload as JSON) and resume after a restart; `StatusHub.UpdateQueue` puts them into the snapshot and `queue` events, `QueueList.vue` (on the page `queue`, since the queue concerns every page; a count in the menu bar's end, visible on phones too, leads there and the create page keeps only `QueueOverview`) shows them with move and remove, each with why it waits (`queueModels.ts` mirrors the queue's rules, counting down the window from `StatusSnapshot.BundleWindowSeconds`), under `QueueOverview.vue`, one line with the three models and which holds the memory. Which large model besides YuE2 holds the memory is decided in one place, `Memory/ModelMemory.cs`: the lyrics writer, `VoiceConverter`, `SpeechLab` and `ImageMaker` claim one shared slot (`LargeModel`, compare-and-swap, so two of them never both have it) and give it back, and the queue only asks `ModelMemory.Holder`; a new model is one `LargeModel` entry, the others wait without knowing it. Against YuE2 each side claims before it looks: `WorkerHost.ExpectSongs` counts a command as busy from before it is sent until its `started` event (the lyrics writer or a conversion would otherwise shut down a worker that has a command in its pipe), while `ModelMemory.TryClaim` takes the slot and then looks at `WorkerHost.InUse` again. The holder goes into the snapshot (`StatusSnapshot.Memory`) and out as `memory` events, so `queueModels.ts` `holderOf` shows what the server decided instead of guessing it from stages. Voice versions keep their own queue in `VoiceConverter`. Transcriptions (`JobKind.Transcription`, payload with the upload's path) wait here too, in a lane of their own: SheetSage2 is small and runs beside YuE2, but inside the worker, which a draft, version or take would shut down, so a running one counts as `WorkerHost.InUse` (not `IsBusy`, songs still start) and they wait for it; one waits for another, for the other models (`memoryTaken`, claimed first like songs) and behind a draft ahead of it unless songs may pass that draft too. The transcription page lists the waiting ones, the queue page the running one and a fifth tile while any is in the works.

### Sharing (`Share/`)

Sharing and exporting are one button and one dialog (`ExportDialog.vue`, one, in `App.vue`; opened by the library and by `SongMenu.vue` through `openExportFor`, which looks the song up in App's library via `registerExportLookup`). The file is made first and then saved or handed to the Web Share API from the dialog's own button, since Safari refuses `navigator.share` once the tap is a few seconds old; without file sharing (desktop browsers) only saving is offered. Exporting (`ExportEndpoints`, `POST /api/songs/{run}/{song}/export`, multipart `format`, `artist`, `genre`, `cover`) makes a small AAC to share (`small`, `.m4a` at `AacEncoder.BitRate`, 128 kbit/s; `AacEncoder`: macOS's own `afconvert`, else `ffmpeg`, 501 without either; tests use `FakeEncoder`), an MP3 (320 kbit/s, ffmpeg with LAME; `afconvert` cannot write MP3), M4A (AAC 256 kbit/s) or a copy of the FLAC, then writes title, album (the run's title), year, track of the run, lyrics, style and seed as comment and the cover through `IAudioTagger` (`TagLibTagger`, TagLib#: ID3v2.3, iTunes atoms, Vorbis comments plus a FLAC picture block; tests use `FakeTagger`, `TagLibTaggerTests` runs real ffmpeg files when it is installed). The browser makes the cover (`export.ts`: drawn from title and a gradient hued by the song id, or a photo cut square, 1000 px JPEG) and suggests the genre from the style's genre building blocks; The dialog remembers format and artist per browser. A chosen photo becomes the song's own cover (`CoverEndpoints`, `GET`/`PUT`/`DELETE /api/songs/{run}/{song}/cover`; `SqliteCoverStore`, `song_covers`, schema version 12, images in `covers/` next to the database under a new name per change), which an export without a `cover` field takes; the library can set it without exporting, shows it by the song, and `SongInfo.CoverUpdatedAt` versions its URL so the player and the lock screen (`MediaMetadata.artwork`) pick up a change. Songs without one keep the drawn cover, which is never stored and only goes into an export. The library's "Choose cover" is the one place a cover is picked (the export dialog only shows which one goes in), and every file that leaves the app carries it with the lyrics: `TaggedFiles` writes tagged temp copies for `audio?download=true` and a version's download (YuE Studio's `audio.flac` is never tagged in place), with `StreamCopies.TagsFor`.

The player streams neither the FLAC nor the share file but a 192 kbit/s AAC copy (`StreamCopies`, `GET /api/songs/{run}/{song}/stream` and `.../versions/{id}/stream`), since the Mac's home upload is too slow for the FLAC's ~1 Mbit/s on the road. `StreamCopyMaker` (hosted service, subscribes like `PushNotifier`) makes it when a song is ready or a version done; older songs get theirs on the first play. Copies lie in `stream/<run>/songN.m4a` next to the database (a version's as `versions/<id>.m4a`), are made again when older than their FLAC (a render writes it in place), are served with range processing and `Cache-Control: no-cache` plus an ETag, and go with the song. They carry the export's tags (`StreamCopies.TagsFor`: title, album, track, lyrics, style and seed, the song's own cover; a version's title adds the voice) without artist or genre; a stamp of them in `<copy>.tags` makes a rename, a new cover or changed lyrics tag the copy again without encoding, always into a temp file that replaces it. Without an encoder, or when it fails, the FLAC is served. Downloads, exports and the Logic page (whose waveform must line up with the notes; AAC adds encoder delay) keep the FLAC.

Loudness (`Share/Loudness.cs`, `ILoudness`, section `Loudness`): exports (FLAC too, re-encoded at 24 bits by `AudioFormat.Flac`), stream copies and videos are brought to `Target` (-14 LUFS, `TruePeak` -1 dBTP) by ffmpeg's `loudnorm` in two passes: the first pass's measurement is cached per file in `loudness` (schema version 22, by path, size and mtime, so a render is measured again), the second (`linear=true`, one gain for the song) is the filter `AacEncoder` and `FfmpegVideoRenderer` put in front (`-ar 48000` behind, loudnorm works at 192 kHz). With a filter, M4A goes through ffmpeg too, since afconvert cannot change the level. A stream copy's `.tags` stamp holds `ILoudness.Key` on its second line, so a changed setting (or a copy from before) is encoded again. Downloads, stems and the Logic page keep the original.

### Music videos (`Video/`, `VideoEndpoints`)

A song as a video to upload, without filmed pictures: `VideoDialog.vue` (one, in `App.vue`, opened through `openVideo` by the library and `SongMenu.vue`) draws the still layers in the browser (`video.ts`: the cover blown up, blurred by drawing it tiny and scaling it up since Safari's canvas long had no `filter`, and darkened; the cover with a shadow, unless `showCover` is off; the title with the export dialog's artist; behind them a `motion`: a field of particles seeded by the song id, whose dots crossing an edge are drawn on the other side too, or a plasma ball without glass, lightning from the cover's middle drawn `VideoLayout.PlasmaFrames` times, behind a cover in a square around it with sparks at the ends, without one over the whole frame from a glowing core to the edges, `VideoLayout.PlasmaArea`) as PNGs and shows a still of the result. `POST /api/songs/{run}/{song}/videos` checks each PNG's header for its size (the frame's, or the plasma area's) (`VideoLayout`: 1920×1080, or 1080×1920 with everything above the bottom fifth the apps cover; its band for the analyzer is mirrored in `video.ts`'s `videoLayouts`) and queues a `VideoState` in `VideoMaker` (hosted service, one at a time, unfinished ones start over after a restart; it does not wait for the models since ffmpeg needs CPU, not their memory, but counts in `BusyInfo` as `video`). `FfmpegVideoRenderer` (`IVideoRenderer`; tests use `FakeVideoRenderer`, `VideoRendererTests` run the real ffmpeg when it is installed) builds one filter graph from ffmpeg's own filters, no fonts needed: every picture is read once and repeated with `loop`; particles scroll up through two stacked copies (`crop` with `t`) and their alpha is multiplied by the bass (a 30–250 Hz `showcqt` averaged to one pixel); the plasma ball's frames are stacked once (`vstack`, then `loop`) and a `crop` jumps between them twelve times a second in an order that repeats only after frames² steps, its alpha multiplied by a steeper bass pulse; the analyzer's bars (`VideoLayout.Bars`, 48 or 27 of `BarPitch`) are computed before as the app's own analyzer computes them (`SpectrumBands`: ffmpeg decodes to mono floats, then Web Audio's 8192-point Blackman FFT with its smoothing and -90 to -20 dB scale, the loudest bin per log band from 30 Hz to 16 kHz, bars rising at once and falling at the app's pace; `showcqt`, linear in loudness, left the highs flat), read back as a raw grey video one pixel high, drawn as columns by `geq` and cut by a gap mask, the wave `showwaves`, both as alpha on the video's `Color` (the cover's most vivid hue, `coverColour` in `video.ts`; schema version 18) or the accent; the title fades in, the whole fades from and to black. Length from `ffprobe`, else `result.json`; progress from `-progress pipe:1`. Output: H.264 High CRF 18, yuv420p, 30 fps, AAC 320 kbit/s 48 kHz, `faststart`. That is hundreds of megabytes for a photo video, right for YouTube (which encodes again) but not for a messenger: the dialog's share button asks `GET /api/videos/{id}/file?small=true`, which `VideoMaker.SmallAsync` makes on the first request (`IVideoRenderer.ShrinkAsync`: 720p, CRF 25 capped at 2.5 Mbit/s, AAC 128 kbit/s; one at a time, to the end even when the request gives up) and keeps as `small.mp4` beside the video; the download stays full. Files in `videos/<id>/` next to the database (`SqliteVideoStore`, `song_videos`, schema version 17, `color` 18), deleted with the song, not in the backup. A finished video replaces the song's older finished or failed ones in its format (`VideoMaker.ReplaceOlder`; the old one stays watchable until then, the other format is kept), and the library shows a video button by songs with one (`SongInfo.VideoFormats`, refreshed through `LibraryChanged`). Progress goes out as `video` events and the snapshot's `Videos`; the queue page lists those in the works.

A photo video (`VideoState.Media`, a subfolder of `MontageOptions.ResolvedMediaRoot`, default `~/Pictures/Tonwerk`, listed by `GET /api/videos/media` through `MediaFolders`, which is also the path guard; `Motif`; schema version 20) replaces the blurred cover with the folder's photos and clips cut to the beat. `VideoMaker` first runs `IMontageBuilder` (tests use `FakeMontage`; `MontageBuilderTests` run the real ffmpeg and, with `YUEUI_MONTAGE_PYTHON` or the default environment, the real planner): `MontageBuilder` runs `Video/yueui_montage.py` with its own Python (`Montage:Python`, made by `deploy/install-montage.sh`, `setup-mac.sh --montage`), which finds beats, downbeat, per-beat energy and section changes with librosa, cuts on bar lines (two bars quiet, one in between, half a bar loud, always at a section, 0.6 to 6 s), judges photos and video samples by sharpness and exposure and, with a motif, by CLIP (open_clip, multilingual `xlm-roberta-base-ViT-B-32` by default, loaded only then, a failed load drops the motif with a note), drops near-duplicates (dHash, or CLIP embeddings), takes the best units (a clip gives at most one per four seconds) in capture order, and writes `plan.json` plus every photo as a JPEG still at twice the frame size (HEIC and EXIF turns handled by Pillow, a photo of another shape whole over its blurred self). Then each shot is one ffmpeg run of exactly its frames (`MontageBuilder.Frames`, counted from the song's start so cuts stay on their beats): `zoompan` over the still, or the clip from its sample, HLG/PQ tone mapped where ffmpeg has zscale, cut or blurred to fit, last frame held; all encoded alike with one time base and joined by the concat demuxer into `montage.mp4`. `FfmpegVideoRenderer` takes that as input 0 instead of the looped PNG, overlays the browser's `shade.png` (darkening, `VideoLayers.Shade`), and the rest is the cover video's graph; motion layers are refused. Work folder and montage are deleted after every run. `ReplaceOlder` only replaces videos with the same `Media`. The montage takes 60 % of the progress. Untested on a Mac and with real photos or CLIP weights.

### Notifications (`Push/`)

Web Push, so a phone hears when a song, transcription or lyrics draft finishes (on iOS only the home-screen app, over HTTPS). `PushNotifier` is a hosted service that subscribes to `StatusHub` like a browser (`Subscribe(checkStudio: false)`) and sends on the change to finished, cancelled songs excepted; texts in `PushTexts` (de/en per subscription, not `i18n.ts`, since no page need be open). `PushStore` keeps the VAPID key pair and subscriptions in `push.json` (`PushOptions`), made on first use; a new key pair orphans every subscription. `WebPushSender` (`IPushSender`, Lib.Net.Http.WebPush) drops subscriptions the service answers 404/410 for; tests replace it with `FakePushSender`. Frontend: `public/manifest.webmanifest` (icons: a sound wave across five staff lines, on Aura's emerald; `public/favicon.svg` and the sources in `ClientApp/icons/` are rendered to the PNGs by `icons/render.sh`), `public/sw.js` (shows every push, Safari revokes silent ones; its fetch handler is for offline playlists, see Playlist, and takes the app network first, so no stale build is served while the Mac answers), `push.ts` and `SettingsMenu.vue` (the cog at the menu bar's end: notifications, language and, in standalone mode, a reload). The home-screen app on iOS resumes from memory instead of reloading, so it would run an old build until closed: `vite.config.ts` (`buildVersion`) compiles a build id into the app and writes it to `version.json`, and `update.ts` compares them when the app becomes visible and on every snapshot (a deploy restarts the server), then `App.vue` offers a reload.

### Backup (`Backup/`, `BackupEndpoints`)

`CloudBackup` (hosted service, after module-o-mat's `RemoteBackupRunner`/`RemoteBackupScheduler`) backs up into a Nextcloud over WebDAV (`WebDavClient`: MKCOL and PUT with Basic auth and an app password) every night at `BackupOptions.At` (section `Backup`; empty for manual only) and on `POST /api/backup`; off until `NEXTCLOUD_WEBDAV_URL`, `NEXTCLOUD_USERNAME` and `NEXTCLOUD_APP_PASSWORD` (module-o-mat's names) are set: environment variables first, then `BackupOptions.EnvFile` (`~/.config/tonwerk/nextcloud.env`, read on every use), then the `Backup` settings as a fallback the tests use; none of them goes into the repo. Each run uploads `tonwerk-<weekday>.zip` (seven rotating) with `yueui.db` copied through SQLite's online backup and `push.json`, then, with `Files`, every song folder, version FLAC, stem, cover, recorded voice, take and transcription that is new or changed since its last upload (size and mtime per remote path in `backup.json` next to the database, saved every 20 files). Nothing is deleted remotely. Left out: streaming copies, the speech lab's env/models (only `speech/voices` and `speech/takes`), songs `WorkerHost.IsWorkingOn`, files younger than `Settle`. Uploads are I/O only, so it does not wait for the models. A file Nextcloud refuses for the moment (423 lock left by a cut-off upload, 429, 502–504, timeout: `WebDavException.Transient`) is tried three times and then left for the next backup while the rest goes on; the run then counts as failed so the nightly one retries. A failure is pushed (`PushTexts.BackupFailed`) and the nightly one retried after `RetryAfter`; the settings menu shows the last run and starts one. `.gitignore`'s Visual Studio rule `Backup*/` has an exception for this folder. Tests fake the server through the named `HttpClient` (`FakeNextcloud`).

### Log (`Logs/`, `LogEndpoints`)

`LogStore` collects what would otherwise need SSH: `LogStoreProvider` (an `ILoggerProvider`, so `Logging:LogLevel` applies) hands it every server message with a source taken from the logger's namespace (`LogSources.ForCategory`: worker, queue, lyrics, voices, speech, video, export, logic, backup, push, else server), `WorkerHost.AddLog` the worker's stderr and events (its in-memory `Log` for the snapshot stays), and `deploy/update.sh`'s own file (`LogOptions.ResolvedUpdateLog`, lines `yyyy-MM-dd HH:mm:ss message` in local time, untimed lines continue the one before) is read along as source `update`. Lines are JSON in one file per UTC day (`logs/tonwerk-yyyy-MM-dd.jsonl` next to the database), written under a lock and flushed at once, so a query sees everything before it; files older than `RetentionDays` go when a day's file opens, and above `MaxFileBytes` a day takes only warnings and errors. A write that fails is dropped, never thrown at what logged. `GET /api/logs` reads newest first (files from the newest, keeping the last matches of each); `GET /api/logs/report` (`LogReport`) is plain text for a chat: build with commit (the informational version), `update/deployed`, worker state, which engines are local, `BusyInfo`, and the last day's warnings and errors with up to five earlier lines of their source; it leaves out settings, keys and addresses. The page `LogPage.vue` (view `logs`, under tools, loaded like the lab) filters by source, level and text and copies the report through `copyPending` (`clipboard.ts`), which hands Safari a `ClipboardItem` with the pending text since the fetch outlasts the tap; where that fails it shows the report to copy by hand. `.gitignore`'s rule `[Ll]ogs/` has an exception for this folder.

### Monitoring (`Monitoring/`, `deploy/monitoring/`)

Metrics and logs for a Prometheus/Loki/Grafana stack that runs on another machine (a Proxmox container over Tailscale), never on the Mac, whose memory belongs to the models. `GET /metrics` (`MetricsEndpoints`, outside `/api`, off with `Monitoring:Metrics`) writes Prometheus' text format by hand (`PrometheusText`, no client library): worker state, `tonwerk_memory_holder` (yue2 from `WorkerHost.IsBusy`, the rest from `ModelMemory.Holder`), `BusyInfo`, the `JobQueue`'s waiting jobs (`StatusHub.Queue`, not a snapshot, which would scan for YuE Studio), disk and process. `JobMetrics` (hosted service, subscribes like `PushNotifier`) counts finished jobs by kind and outcome and their working time (from the first state past `queued`, a song's from its `Stages`) into `Histogram`s, and keeps what waits or runs. Every line the `LogStore` writes passes `LogFeed` (counted for `tonwerk_log_lines_total`; a class of its own since `LokiShipper` logs through the same store, so the store taking the shipper would make the logger need itself), which queues it for `LokiShipper` when `Monitoring:Loki:Url` is set (bounded, oldest dropped). The shipper pushes batches to `/loki/api/v1/push` with labels `app`, `host`, `source`, `level` only, retries 5xx/429/timeouts four times, then drops; its `HttpClient` has `RemoveAllLoggers()`, since its request logging would otherwise feed itself forever. The update log is not shipped. `deploy/monitoring/`: compose file, Prometheus reading one `targets/*.yml` per app (`file_sd`, `__scheme__` per target), Loki single-binary on disk, Grafana provisioned with both data sources and `grafana/dashboards/tonwerk.json`. The dashboard's metric names are a contract with `MetricsEndpoints`; rename neither alone. Tests fake Loki through the named `HttpClient` (`FakeLoki`). The stack was started once in the cloud container against a local Tonwerk; not yet on the Proxmox or against the Mac.

### Storage (`Storage/`, `StorageEndpoints`)

The page `StoragePage.vue` (view `storage`, under tools; the library's free-space line links there) shows where the disk goes. `GET /api/storage/overview` (`StorageScanner.Scan`) measures each part anew like `du`: a part moved by `deploy/move-to-volume.sh` is followed through its link, links inside are not (Hugging Face snapshots count once), and each part names the volume it lies on (`DriveInfo`, longest mount prefix of its real path). Groups: `work` (songs without transcriptions, transcriptions, versions' FLACs, stems, swaps, videos, covers, painted candidates, speech takes and voices, reference voices, LoRAs, each with its 30 largest entries deleted through their own endpoints by `kind`), `app` (streaming copies incl. versions' `.m4a`, logs, the data folder's loose files) and `models` (shown only, never deleted). Files in `versions/`, `stems/`, `swaps/`, `videos/`, `covers/` without a database row and older than a day count as `Orphaned`. `POST /api/storage/cleanup/{target}`: `stream` (`StreamCopies.ForgetAll`, made again on the next play), `images` (finished candidates), `videos` (finished videos), `orphans`, `failed` (failed or cancelled versions, stems, swaps and videos with files left, `StorageOverview.Failed`). Songs with one star are offered as a whole and deleted one by one through `DELETE /api/songs/…`; unrated songs are only counted like the library's review filter and linked there.

### Playlist and database (`Data/`, `PlaylistEndpoints`)

The app's own state lives in one SQLite file (`DataOptions`, section `Data`, default `yueui.db` next to `push.json`), opened by `SqliteDatabase`, which creates the file on first use and versions the schema with `PRAGMA user_version` (add a step, never edit an old one; same pattern yue-to-logic-pro used). It holds the playlists (`SqlitePlaylistStore`): a row each in `playlists`, their song ids in `playlist_songs`, at least one always (the last cannot be deleted, so "add to playlist" has somewhere to go); titles given to runs (`SqliteRunTitleStore`, `run_titles`); and song ratings, 1 to 5 stars per song id (`SqliteSongRatingStore`, `song_ratings`, no row when unrated). `SongLibrary` lays the ratings into `SongInfo.Rating` and forgets them with deleted songs; notes per song work the same way (`SqliteSongNoteStore`, `song_notes`, schema version 14, `SongInfo.Note`, `PUT /api/songs/{run}/{song}/note`, trimmed, empty deletes), edited in `SongNote.vue` under the song, which saves on its own (debounce, blur, page hidden, close) with `keepalive`, and the library's note button is filled while one is written; `PUT /api/songs/{run}/{song}/rating` publishes a `library` event, and the frontend keeps an optimistic copy in `ratings.ts` for the library and the player. A rename (`PUT /api/runs/{run}/title`) never touches the folder, since its name is the song id that playlists, links, the worker's states and YuE Studio rely on; `SongLibrary` lays the title over the worker's (`RunInfo.OriginalTitle` keeps that one) and `WorkerHost.RunRenamed` renames the queue's songs. `SongLibrary` still lists songs when the database cannot be read. `PUT /api/playlists/{id}/songs` replaces a playlist's songs as a whole and only accepts ids of existing songs; `GET /api/playlists` leaves out songs deleted since. Which playlist a page shows (and a single tap adds to) is chosen per browser (`playlist.ts`, `localStorage`); with more than one, the plus by a song (`PlaylistToggle.vue`, library and player) opens a menu of them. On the server rather than in `localStorage`, because the phone's home-screen app, its Safari and the Mac each have their own storage. A playlist can be kept offline per browser (`offline.ts`, the cloud button in `PlaylistView.vue`, ids in `yue-ui.offline`): `syncOffline` puts its songs' stream copies and covers into the Cache Storage `tonwerk-offline` (fetched with `cache: 'no-store'` and `If-None-Match`, so a render's new audio replaces the copy and the service worker does not answer its own check), drops what no offline playlist wants (never while the library is unknown), and runs after playlist or library changes and on `online`. `public/sw.js` answers `/stream` and `/cover` from that cache first, cutting Range requests into 206 answers itself (Safari plays media only from a source that does), keeps `/api/library` and `/api/playlists` network first with the last answer as fallback, `/ui/assets/` cache first (hashed names) and the rest of `/ui/` network first; `push.ts` registers it also where there is no Web Push. `sw.test.ts` runs the script with a fake `self`. Untested on an iPhone.

### Sketches (`Sketches/`, `SketchEndpoints`)

A written song sketch (structure, chords, lyrics, melody ideas) becomes a song. The local lyrics models cannot write a whole melody bar by bar in a strict format, so `ClaudeSketchModel` (`ISketchModel`; tests use `FakeSketchModel`, `ClaudeSketchModelTests` run the real Anthropic SDK against a fake SSE handler on the named `HttpClient` `anthropic`) asks Claude through the official `Anthropic` NuGet package (streamed, adaptive thinking, `Sketch:Effort`, structured output with the strict JSON schema `ClaudeSketchModel.Schema`) for a `SketchPlan`: tempo, key, style, sections with `parts` and `energy`, and per bar chords, the vocal line and its syllables in a small notation (`PITCH:LENGTH` in sixteenths, documented in its system prompt). Everything after that is deterministic: `SketchScore` lays the plan out (ties merged, bars repaired or cut, extended chords reduced to YuE2's vocabulary with the add9 kept for the MIDI, a syllable check against the bar's lyric) and writes YuE2's ABC through `YueToLogic.Core`'s `AbcScoreWriter`, the lyrics from each section's `lyrics` lines verbatim (bar lyrics are only for the check) and a `SongRequest` with planning `full`, beside it what ACE-Step reads of the plan (`SketchResult.Ace`, `SketchScore.AceRequest`: lyrics, style as caption, tempo, key spelled as its picker, metre where it knows it, length 10 to 600 s, language by `LyricsTimer.Language`; no melody or chords, ACE-Step reads no score), which "Als ACE-Song" lays over the ACE page's form; `SketchArranger` plays piano, pad, bass and drums per section and renders the draft with `MidiRenderer`. The page picks the model (`SketchRequest.Model`, one of `SketchOptions.Offered`: `Model` first, then `Models`; kept per browser as `yue-ui.sketchModel`), stored on the job from the start so a restart plans with it. The key comes from `Sketch:ApiKey`, `ANTHROPIC_API_KEY` or `~/.config/tonwerk/anthropic.key`, read on every plan; without one `POST /api/sketches` answers 501. `SketchMaker` (hosted service) plans one at a time, jobs in `song_sketches` (schema version 26, `SqliteSketchStore`, the job as JSON), queued ones resume after a restart, half-made ones fail; it claims no `ModelMemory`, since nothing runs on the Mac, and pushes when done (`PushTexts.Sketch`). The page `SketchPage.vue` (view `sketch`, under tools) polls while a plan is made and hands the request to the form (`fromSongRequest`) or the score to the Logic page. Untested against the live API (no key in the cloud container).

### Insights (`Library/Insights.cs`, `GET /api/insights`)

What the rated songs were made with against their stars: style blocks (the style split at commas, lower-cased, once per song), engine, quality, LoRA, full steps, length bucket and instrumental, from `ListRuns` and each rated song's `ReadRequest`, computed per call. Entries need `MinCount` songs and are sorted by a score that adds `Prior` songs of the overall average. `InsightsPage.vue` (view `insights`, under tools) shows them; `insights.ts` `provenStyleBlocks` (style blocks scoring above the average) is the create page's style-block tab "proven" (`StyleBlocks.vue`), which stays away while there are none.

### Prompt templates (`TemplateEndpoints`, `SqlitePromptTemplateStore`)

A template is the form's style and parameters under a name (`prompt_templates`, schema version 16, names unique through an upper-cased `name_key`, addressed by id so a rename keeps it). The settings are opaque JSON to the server; `form.ts` decides what goes in (`templatePartKeys`: style with instrumental, seed, parameters, voice, never title, lyrics or score) and lays a template over the form with `applyTemplate` (only the keys it holds, type-checked like a stored form; a score in the form keeps its planning). `templates.ts` holds the list and the template the form was last filled from, which saving offers to overwrite; `TemplatePicker.vue` sits at the top of the create page, `TemplatesPage.vue` (view `templates`, under tools) renames and deletes. Being in `yueui.db`, they go into the nightly backup.

### API

Minimal API, endpoint groups per file: `WorkerEndpoints` (status, SSE via `TypedResults.ServerSentEvents`, generate, render, cancel, stop, worker shutdown), `TranscriptionEndpoints` (upload up to 300 MB, list, cancel, score, ZIP, delete), `LyricsEndpoints` (lyrics drafts), `PushEndpoints` (VAPID key, subscriptions, test push) and `LibraryEndpoints` (library listing with sizes, FLAC with range processing, score, deleting songs and runs, free space). Deleting is refused (409) while this server's worker is on the song (`WorkerHost.IsWorkingOn`) and publishes a `library` event so every open browser reloads. `SongLibrary` reads run folders and only accepts names matching the worker's patterns, which is also the path-traversal guard. Commands to the worker answer 202; the result arrives as events. JSON is camelCase with enums as camelCase strings. The server binds to 127.0.0.1 only; remote access is `tailscale serve --https=8443` (443 on this Mac already proxies another service), there is no login.

### Native apps (`apple/`)

The UI moves into native SwiftUI apps for iPhone and Mac (decided 2026-10-15); the server stays as it is and the Vue frontend keeps running until the apps cover it. The contract is the OpenAPI description at `/api/openapi` (`ApiDocument`: title, HEAD operations left out, a multipart form's `allOf` merged into one object since Swift's generator wants one): every endpoint has `.WithName(...)` (the operation id, PascalCase, verb first) and declares its answers with `.Produces<T>`, `.ProducesProblem`, `.ProducesValidationProblem` or, for files, `ApiDocument.ProducesFile` (without a type `Produces` leaves the content out). `OpenApiTests` holds every operation to that and compares the description with the copy in `apple/TonwerkKit/Sources/TonwerkAPI/openapi.json`; after changing an endpoint run them with `TONWERK_UPDATE_OPENAPI=1`, which also writes real answers as the Swift tests' fixtures. The event stream is described by `Status/ServerEvents.cs` (one property per event name; add one there with every new `Publish` name), decoded by hand in TonwerkKit's `ServerEvent`. Answers in `YueToLogicJsonContext`'s JSON are declared as `JsonElement`, since a generated schema would claim camelCase enums. `apple/TonwerkKit` is a Swift package (swift-openapi-generator at build time, `Tonwerk`, `ServerAddress`, `TonwerkDates` for .NET's seven fractional digits); CI builds and tests it on macOS (job `TonwerkKit (Swift)`); the cloud container has no Swift (download.swift.org is blocked). The OpenAPI description leaves out the string that the web JSON defaults allow for every number (`ApiDocument.NumbersOnly`), since Swift's generator would make such a field an untyped container.

The app (`apple/Tonwerk.xcodeproj`, one SwiftUI target for macOS 14 and iOS 17, folder `apple/Tonwerk` synchronized, so new files need no project edit) is only its entry point; screens, `AppModel` (server address in `UserDefaults`, library, playlists, the event stream reconnected every 3 s) and `Player` (AVPlayer on the stream copies, Now Playing and remote commands) are TonwerkKit's `TonwerkUI` target (the queue page like `QueueList.vue`: finished songs until hidden, `AppModel.hiddenFinished` per run of the app, "Als Playlist" from `readySongIds`, the worker's log from the snapshot and `log` events, `workerLog`), Swift 5 mode, so `swift build` compiles them. `Song` is the library song with its run's title and its stream and cover addresses. Its bundle id is `de.bvelop.yueui.app` (internal, keeping the old name like the repo): `de.bvelop.tonwerk` belongs to the Synth repository's app with the plugins (and its AUv3s' ids sit under it), and two apps with one id replace each other on a device and share the Mac's sandbox container. The Mac build signs ad hoc (`CODE_SIGN_IDENTITY[sdk=macosx*] = -`, sandbox with outgoing network only), the iPhone needs a team. CI builds the app for both platforms unsigned with `-skipPackagePluginValidation`. The create form (`CreateForm`, `CreateView` with `ScoreSection`, `AdvancedSection`, `StyleBlocksView`) follows `form.ts` (a lyrics draft's photo scaled like `photo.ts` by `CoverPhoto.scaledJPEG` and kept with the page only); `AbcScore` (transposition, key change, vocal range) and `StyleBlocks`/`SectionTags` are ports of `abcTranspose.ts`, `styleTags.ts` and `lyricsTags.ts` held to the same tests, so change both sides together.

The Logic page (`LogicSession`, `LogicView`, `LogicPlayer`) works from a `ScoreSource`, a library song or a MIDI file or `score.abc` of one's own (uploaded as `file`, without a recording to play along or to go into the project), converts on the server and plays with `AVAudioSequencer`, a track to a Core MIDI output (`MidiOutputs`, Bluetooth MIDI through Apple's dialogs) or to the app's own sound. That sound is Tonwerk's synthesizers: the `TonwerkDSP` target holds the Synth repository's plain C++ DSP (`src/dsp` copied unchanged into `dsp/`, so copy again when the browser's synths or the plugin change) behind a C interface (`include/TonwerkDSP.h`, `Synth.cpp` with sixteen voices; `Effects.h` the delay ported from the plugin and, instead of the convolution, an eight-line feedback delay network calibrated with noise to the same level), wrapped as an in-process AUv3 (`TonwerkSynthUnit`, `aumu Twap Bvlp`, `registerSubclass`, no extension). `SynthSound` is the patch JSON (`normalizePatch` with the same defaults and ranges), `SoundLibrary` the server's named and per-track sounds, the instruments page (`InstrumentsSession`, `InstrumentsView`, `SoundEditor`, `TestKeyboard`) edits both and the MIDI instrument library. Drums still play Apple's sampler. Its `LogicForm` also carries the web form's vocals (backing vocal parts, key, chorus only, doubling by octaves, sent as `arrangement.harmony` and `doubling`) and, for a library song, the stems: the newest set with `vocals`/`vocals_dry` preselected as the export's `stems`, "Stems erzeugen" opening the voices page (`openStems`), and with Basic Pitch installed bass and drums from the stems (`bassStems`/`drumStems` on convert and export, the picked set where it has the stem, else the newest that does), the song's sets read on opening with `AppModel.liveStems` laid over them.

The voices page (`VoicesSession`, `VoicesView`, `Voices.swift`) covers the web page's three panels: reference voices (a file picked, copied into the temporary folder as `PickedFile`, trimmed by start and end that the server cuts), stems (a library song or a file, model and dereverb, each stem played on `AudioPreview` with the set's `peaks`, saved or turned into MIDI through `api/stems/{id}/{name}/midi`) and the voice swap; "Mit Stimme singen" in a song's menu is `SingSheet`, with `VoiceSettings` kept between songs. These calls go through `URLSession` by hand and decode the generated types with `JSONDecoder.tonwerk()`, since their answers differ by which voice service the server runs (501, 502) and what matters is the problem's words. `version`, `stems` and `swap` events fill `AppModel.liveVersions`, `liveStems`, `liveSwaps`; the queue page lists the unfinished ones (`voiceJobs`).

Music videos (`Video.swift`, `VideoSheet.swift`, "Musikvideo …" in a song's menu) draw the same PNG layers as `video.ts`, ported step by step onto a top-left `VideoCanvas` over Core Graphics and Core Text (same layouts, the browser's Mulberry32 and FNV-1a so a song gets the same particles and bolts, `coverColour`), with a scaled preview, and send them to `POST api/songs/{run}/{song}/videos`; change both sides together. The song's own cover or the drawn `ExportCover`, the timed lines from `GET .../timing`, the artist from the share dialog. `video` events fill `AppModel.liveVideos`; the queue page lists the unfinished ones (`videoJobs`). A finished video plays in `VideoPlayer` and is downloaded to share or save.

The transcription page (`TranscriptionSession` in `Transcription.swift`, `TranscriptionView`) covers `TranscribePanel.vue` and `AudioMidiPanel.vue`: an upload to SheetSage2 (`api/transcriptions`, multipart `file`, `task`), the finished ones with "Als Partitur übernehmen" (`CreateForm.useScore`), their ABC, the score or ZIP saved, delete, and a recording to MIDI through `api/audio-midi`. `transcription` events fill `AppModel.liveTranscriptions`; the running one has a queue card and a model tile (`QueueModel.transcription`, working beside YuE2), the waiting ones are queued jobs.

The log page (`LogSession` in `Log.swift`, `LogView`) is `LogPage.vue`: `GET api/logs` decoded into its own `LogLine` so the time stays the server's text for the next page's `before`, and the report copied straight to the clipboard (`Clipboard`), which a native app may write after the request.

The storage page (`StorageSession` in `Storage.swift`, `StorageView`) is `StoragePage.vue`: `GET api/storage/overview` measured on every visit, the volumes with Tonwerk's share, the cleanups (`api/storage/cleanup/{target}`, offered only where they free something), one-star songs deleted one by one through the library's endpoint, and each part's largest entries deleted through the endpoint of their kind (`AppModel.deletePath`); models are only shown.

Templates (`Templates.swift`, `TemplatesView.swift`) are `templates.ts`, `TemplatePicker.vue` (at the top of the create form) and `TemplatesPage.vue`: `TemplateSettings` reads and writes the web form's names (`quality`, `cot`, `voiceId`, …) so a template moves between browser and app, lays itself over `CreateForm` as `applyTemplate` does, and keeps a template's voice when the app overwrites it, since the app's form has none.

The speech lab (`SpeechSession` in `Speech.swift`, `SpeechView`) is `SpeechLab.vue` and `SpeechCleanPanel.vue`: recorded voices (`VoiceRecorder`, AAC through `AVAudioRecorder` without the phone's voice processing, at most 30 s, or a picked file; the app asks for the microphone, `NSMicrophoneUsageDescription` and the Mac's `audio-input` entitlement), a text spoken by the chosen models (`api/speech/takes`), cleanups (`api/speech/cleanups`), all played on an `AudioPreview`. `speech` events fill `AppModel.liveSpeech`, which the page lays over its `GET api/speech` (`SpeechSession.merge`, newer `updatedAt` wins); the queue page lists unfinished takes (`speechJobs`) and the `speech` tile counts them.

ACE-Step (`AceSession` and `AceForm` in `Ace.swift`, `AceView`) is `AcePage.vue` with `ace.ts`: `AceForm` keeps `aceForm`'s fields and defaults (stored in `UserDefaults`, a field of another type taking its default), builds the request as `toAceRequest` does (`request`, what a task does not read sent as null) and reads one back as `fromAceRequest` (`init(request:)`). The form lives on `AppModel.aceForm`, since "Alles übernehmen" on an ACE-Step song (`useInForm`, by `Song.engine`) fills it from `GET api/songs/{run}/{song}/ace` before the page opens. `ace` events and the snapshot fill `AppModel.liveAce`, laid over `GET api/ace` (`AceSession.merge`); the queue page lists unfinished jobs (`aceJobs`) and the `ace` tile counts them.

The analyzers (`Spectrum.swift`) are `spectrum.ts` and `SpectrumBars.vue`: `SpectrumAnalyzer` takes what plays from an `MTAudioProcessingTap` on the player's item (`SpectrumTap`) or a tap on `LogicPlayer`'s main mixer and reads it as Web Audio's analyser does (8192-point Blackman FFT, smoothing 0.75, -90 to -20 dB, log bands from 30 Hz). The player bar has a small one, the full-screen player a large one and the glows with the beating cover (`BeatLevels`, switches `nowPlayingAnalyzer` and `nowPlayingEffects`, still under Reduce Motion), in `Player.coverColour`; the Logic and backing vocals pages one above the piano roll.

The insights page (`Insights.swift`, `InsightsView`) is `InsightsPage.vue`, read anew on every visit into `AppModel.insights`; `Insights.proven` is `provenStyleBlocks`, offered by `StyleBlocksView` as the group "★ Bewährt" while there are any.

The sketch page (`SketchSession` in `Sketch.swift`, `SketchView`) is `SketchPage.vue`: a sketch typed or loaded from a text file, wishes and the Claude model (kept in `UserDefaults`, empty for the server's default) go to `POST api/sketches`; the page polls every 4 s while one is being written and reads a sketch as `SketchDetail`, since before the plan the answer is only its job. A plan goes into the create form (`CreateForm.take`) or the ACE-Step form (`useAce`, `AceForm(request:)` from `SketchDetail.ace`), its MIDI draft and score are saved as files; "Auf der Logic-Seite öffnen" hands the score over as a file (`openInLogic(file:)`).

The backing vocals page (`HarmonySession` in `Harmony.swift`, `HarmonyView`) is `HarmonyPage.vue`: a MIDI file or `score.abc` (uploaded as `file`) or a library song with a score goes through `POST api/logic/convert` with only the harmony switched on (`HarmonySettings.options`, the parts, key, chorus only and chord track kept in `UserDefaults`); the preview is the Logic page's `PianoRoll` and `LogicTransport` on a `LogicPlayer` of its own, every part in the app's sound for its track, and the MIDI file (`LogicConversion.midi`) is saved as `<melody>-begleitstimmen.mid`. Parts are not routed to MIDI instruments here; that stays the Logic page's, which the page opens with the same melody (the parts themselves would not survive, since the converter reads `Harmony …` tracks as generated).

### Frontend (`src/YueUI.Api/ClientApp`)

Vue 3 + TypeScript + Vite, no router, no state library. `App.vue` holds the state and the event subscription and switches pages (`view.ts`: create, queue, transcribe, songs, playlist, voices, logic, harmony, instruments, lab, logs, templates, ace, insights, sketch, kept in the URL hash, shown with `v-show` so a page keeps its input; the menu bar lists create, songs and playlist and groups transcribe, voices, logic, lab and the log under a "tools" submenu whose badge sums theirs, and the queue is only the hourglass at its end; a song's address is `#/songs/<run>/songN`, which scrolls the songs page to it and marks it, and player, playlist and queue link there; `#/logic/<run>/songN` opens a song on the Logic page) through a PrimeVue `Menubar`; `player.ts` owns the one audio element (in `PlayerBar.vue`, outside the pages, so playback survives a page change) and what plays next; `playlist.ts` holds the playlists and the active one; `api.ts` is the only place that talks to `/api`, apart from the Logic page's own `logic/api.ts`; `types.ts` mirrors the API's records by hand; `i18n.ts` holds every German and English string; `form.ts` maps the form to `GenerateRequest` and keeps it in `localStorage`, and a song's `request.json` (`GET /api/songs/{run}/{song}/request`, `SongRequest`) back into the form for "use everything" (`SongMenu.vue` and the library's song actions). YuE Studio's `request.json` keeps only style, lyrics, planning, seed and score, so `WorkerHost` writes each song's generate command (minus batch, seed and LoRA path) as `yueui-request.json` beside it when the song is done (`SongLibrary.SaveAppRequest`), and `ReadRequest` takes that first; older songs get at least quality and steps from `result.json`. `styleTags.ts` holds the style building blocks (`StyleBlocks.vue`), single words from YuE v1's `top_200_tags.json` (YuE2 has no tag list) plus language, tempo and the descriptive phrases of YuE2's own examples, and inserts or removes them in the comma-separated style. `abcTranspose.ts` transposes a score by semitones in YuE2's dialect (an accidental holds for its letter in every octave until the bar line, as in `YueToLogic.Core`'s `AccidentalTracker`) and respells it in the new key; the − and + by the score field and its key picker (`transposeToKey`, the shorter way) use it, since the model sings the `Vocal` voice at its written pitch. The picker offers all 24 keys: one in the other mode first runs `changeMode` (same root, major to natural minor: third, sixth and seventh a semitone down, chords take the quality their moved notes form, `chordIntervals` being YuE2's vocabulary; minor to major the other way), since YuE2 reads a minor `K:` but only the notes make a song minor. `search.ts` filters the library in the browser (the listing already carries style and lyrics), in title and style or in the lyrics, never both, since common lyric words would bury the title hits. `sort.ts` orders it (date, stars, duration; a run keeps its songs together and moves by its best one), remembered per browser in `localStorage`. `review.ts` collects songs left unrated longer than a number of days (per browser, default 7; runs without a date never count): the rating filter's `review` entry lists them to be heard, rated or deleted, songs rated meanwhile stay listed until the filter changes, and the count is the songs page's menu badge and a hint above the search. Nothing is deleted by itself. The Logic page (`LogicPage.vue`, `components/logic/`, `logic/`) is yue-to-logic-pro's page ported: options, presets, instruments, a piano-roll preview and playback through Web MIDI (`logic/midiPlayer.ts`, Chromium and Firefox, a feature test in `midiUsable`) or Web Audio; it is loaded with `defineAsyncComponent` and mounted only once opened, so a normal visit does not fetch instruments or presets. The build writes a Brotli and a gzip copy of every script and style sheet (`precompress` in `vite.config.ts`); `ClientAppAssets` serves the one the browser accepts, since neither Kestrel nor `tailscale serve` compresses, and marks everything under `/ui/assets/` (hashed names) `immutable`. A page loaded on first use whose chunk a deploy removed raises `vite:preloadError`; `update.ts` then reloads when the server has a newer build, unless music plays. Mobile first (the main client is a phone): inputs are 16px to avoid iOS zoom, the player uses `preload="none"` and starts `play()` inside the click, which iOS requires.

UI components come from PrimeVue 4 (styled mode, Aura preset from `@primeuix/themes`), configured and registered globally in `main.ts`, except those only the library needs (`DataView`, `Fieldset`, `Dialog`), which the library's components import themselves so they load with it after the first paint (`defineAsyncComponent` in `App.vue`). The library is `LibraryList.vue` (filter state, paging, a song's address, the play queue, runs with rename and delete) with `LibraryFilters.vue` (search, rating filter, order, the review hint; the values stay in the list through `v-model`), `SongRow.vue` (one song with its note, versions and score), `SongActions.vue` (icons on a wide screen, the "…" menu on a phone) and `SingDialog.vue` (one for the list). Import from `primevue/<name>`, never the `primevue` barrel. `primevueStyles.ts` stops PrimeVue from clearing its list of loaded styles on every component update (each clear made the next update rewrite its `<style>` and restyle the whole page; Safari reloaded the page for its energy use); remove it only once PrimeVue no longer does that. `theme.ts` is Aura with only the design tokens of the components in the bundle, since the full preset carries all ~100; a component used for the first time needs its entry there, and `vite build` fails naming it otherwise (`presetCoversStyles` in `vite.config.ts`). Use a PrimeVue component (`Button`, `Card`, `InputText`, `Rating`, …) instead of styling native elements; adjust the look through the preset's design tokens rather than by overriding `.p-*` classes. `style.css` keeps only the page frame, the app's colour variables (`--accent`, `--text`, `--surface-sunken`, …, mapped onto Aura's tokens so scoped styles share PrimeVue's palette in both themes) and the text helpers `.muted` and `.danger` plus the Logic page's `.hint`; the old `.button`, `.card`, `.link`, `.field` and native input rules are gone, so a text field that should fill its row needs `fluid`. Layout goes into Tailwind utilities, or a component's `<style scoped>` when it is more than a few classes.

Tailwind CSS 4 (via `@tailwindcss/vite`, without preflight) with `tailwindcss-primeui`, which adds utilities for PrimeVue's tokens (`bg-primary`, `text-muted-color`, `bg-emphasis`, …). Cascade layers decide what wins, in this order (declared at the top of `style.css`): `theme, base, primevue, components, utilities`. So utilities override PrimeVue, and PrimeVue overrides the app's own element rules in `base`. Keep global CSS inside a layer; an unlayered rule, including every `<style scoped>` block, beats all of them.

## Conventions

- Commit messages and branch names are German; code, comments and API messages are English. UI strings exist in both languages in `i18n.ts`.
- Comments explain why. New API fields go into the C# record, `types.ts` and, if user-facing, `i18n.ts` together.
